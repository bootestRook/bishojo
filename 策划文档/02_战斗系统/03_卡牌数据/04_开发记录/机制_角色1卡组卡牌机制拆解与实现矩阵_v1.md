# 机制：角色1卡组卡牌机制拆解与实现矩阵 V1

文件职责：作为角色1卡组机制拆解的索引页，只记录共用口径、单卡文件入口和跨卡机制清单。单卡机制细节必须写入 `01_单卡机制矩阵/` 下的一卡一档文件，禁止继续把所有卡牌细节堆进本文件。

最后更新：2026-06-11
当前阶段：Agent C 审核通过；四张角色 1 伙伴卡的只读适配/验证层已归档。

---

## 1. 可扩展维护规则

| 规则 | 要求 |
|---|---|
| 一卡一档 | 每张卡维护一个 `机制_[卡牌名]卡牌实现矩阵_v1.md`，只记录该卡的主动、被动、缺口、验证和归档证据。 |
| 总矩阵只做索引 | 本文件不得写逐卡大表，不得承载超过摘要级别的单卡实现细节。 |
| 新增卡牌 | 新增单卡机制文件后，只在本文件追加 1 行索引，并在状态总表追加 1 行状态。 |
| 批量开发 | 一批卡牌的共用规则写在本文件；单卡差异只写入对应单卡文件。 |
| 查找优先级 | 先查本索引定位卡牌，再打开单卡机制文件；不要全文滚动查找。 |

## 3. 共用实现口径

| 范围 | 口径 |
|---|---|
| 当前实现面 | `tools/card_effect_adapter/`，只读加载卡牌 JSON，生成规范化效果并运行最小验证。 |
| 当前运行时现状 | 仓库未发现 `.gd` / `.cs` 战斗运行时代码，因此本轮不假接入 `BattleManager`。 |
| Godot API | 本轮未触碰 `.gd`、`.tscn`、`.tres`、`project.godot` 或 Godot API。后续若写 Godot 运行时，必须先按仓库规则查询 Godot API。 |
| 待定字段策略 | 对 JSON 中 `null` 的 `damage_type`、`can_crit`、`can_trigger_lifesteal` 输出 `pending_null_rule` warning，不静默推断。 |
| 验证入口 | `node tools/card_effect_adapter/validate_role1_cards.mjs` |

## 6. 后续扩展方式

当角色1卡组扩展到更多卡牌时：

1. 新增 `01_单卡机制矩阵/机制_[卡牌名]卡牌实现矩阵_v1.md`。
2. 在本文件第 2 节追加 1 行索引。
3. 在 `总表_角色1卡组卡牌开发状态_v1.md` 追加 1 行状态。
4. 不把单卡机制表、验证细节或长篇审核结论写回本索引。
